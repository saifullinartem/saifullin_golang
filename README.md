# TripGo

Сервис поездок для курса «Разработка микросервисов на Go». Во второй
лабораторной разделил код на слои, добавил тесты, линтер и OpenTelemetry.

## Запуск

Для работы нужны Go 1.26+, Docker, `tripgoctl` и `golangci-lint` 2.x.

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
make migrate
make run
```

В `environment.toml` включены PostgreSQL и средства наблюдаемости для второй
лабораторной. `make run` сначала читает `.env.example`, затем `.env`. Значения
из `.env` имеют приоритет. Адреса БД и коллектора туда записывает `tripgoctl`.
Файлы `.env` и `.tripgo/` исключены из Git.

Ссылки на Jaeger, Grafana и Prometheus выводит `tripgoctl connect`.

## HTTP API

| Операция | Запрос | Ответ |
|---|---|---|
| Создание | `POST /api/v1/trips` | `201`, поездка и `Location`. Если водитель занят, `409 driver_busy` |
| Получение | `GET /api/v1/trips/{tripId}` | `200`. Если поездка не найдена, `404 trip_not_found` |
| Завершение | `POST /api/v1/trips/{tripId}/finish` с пустым телом | `200`. Если поездка уже завершена, `409 trip_completed` |
| Liveness | `GET /health` | `200`, без обращения к БД |
| Readiness | `GET /ready` | `200` или `503` по результату проверки БД |

Успешные ответы и ответы health/ready возвращаются как `application/json`.
Ошибки операций поездок и роутинга имеют формат `application/problem+json`
по RFC 9457. У `/ready` при недоступной БД остаётся ответ из исходного
контракта, `503` и JSON со статусом `unavailable`.

Невалидный запрос получает `400 invalid_request`, внутренняя ошибка возвращает
`500 internal_error`. SQL, пароли и стектрейс в ответ не попадают. Неизвестный
маршрут получает `404 not_found`, неподдерживаемый метод получает
`405 method_not_allowed` с заголовком `Allow`. Оба ответа имеют формат `Problem`.

В ошибках валидации указан полный путь поля, например `start_point.latitude`.
Исходную причину можно получить через `errors.Is` и `errors.As`. Ошибки
параметров OpenAPI сохраняют имя `tripId` или `Idempotency-Key`.

Пример тела запроса на создание поездки

```json
{
  "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
  "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
  "start_point": {"latitude": 59.9398, "longitude": 30.3146},
  "end_point": {"latitude": 59.929, "longitude": 30.3626},
  "price": 1450
}
```

[Контракт](contracts/openapi/trip-service.openapi.yaml) содержит и операции
следующих лабораторных. Генерация и роутер подключают только три операции
поездок и две проверки состояния из первой работы. Сам контракт и две
существующие миграции не менялись.

## Архитектура

```text
cmd/trip-service -> config + container
container -> конкретные реализации зависимостей

http/trip/{create,get,finish} -> интерфейс usecase -> model/domain
usecase/trip/{create,get,finish} -> интерфейсы repository, txManager, clock, events
repository/trip -> model/domain + PostgreSQL/transaction
infra/{postgres,telemetry} -> pgx, OpenTelemetry, slog
```

У каждого действия есть отдельный HTTP-пакет и usecase. Неэкспортируемые
интерфейсы лежат в `contract.go` того пакета, который их использует.
Например, `usecase/trip/create` нужны только создание поездки, запись истории
и транзакция. HTTP-хендлер работает через интерфейс своего usecase.
Для второго транспорта понадобятся новые хендлеры и их подключение
в контейнере. Usecase и репозитории можно будет использовать повторно.

`container.New(ctx, cfg)` создаёт пул БД, репозитории, менеджер транзакций,
телеметрию, usecase, хендлеры и сервер. В `main` остались чтение настроек,
вызов контейнера, запуск сервера и обработка SIGINT/SIGTERM. Зависимости
передаются явно. Глобальных логгеров и OTel-провайдеров нет.

Правила `depguard` запрещают инфраструктурные и транспортные импорты
в домене. В usecase нельзя импортировать HTTP, pgx, squirrel и API.
HTTP-пакеты не обращаются напрямую к инфраструктуре и репозиториям.

В `domain/trip` находятся модель поездки, валидация и метод `Finish`.
Пакет `model` содержит алиасы доменных типов и структуру записи истории.
Так модель с методом перехода состояния не приходится дублировать.
У `ValidationError` есть поле, причина и исходная ошибка, доступная через
`Unwrap`. Ошибки оборачиваются с `%w`, а `http/domainerror.Problem`
переводит их в HTTP-ответ через `errors.Is` и `errors.As`.

Общая HTTP-логика вынесена в `http/respond`,
`http/response` и `http/routing`. Они отвечают за запись ответов, буферизацию
и маршрутизацию. В `http/trip/convert` доменная поездка переводится
в OpenAPI-ответ для всех трёх хендлеров.

### Транзакции и параллельные запросы

Поездка и её история записываются в одной транзакции `Read Committed`.
Менеджер сохраняет транзакцию в контексте, и оба репозитория используют
её вместо пула. Вложенный `Do` для того же пула берёт текущую транзакцию.
При ошибке, отмене контекста или панике выполняется rollback с отдельным
ограниченным контекстом. После rollback паника передаётся в HTTP Recover.

Частичный уникальный индекс из первой работы не даёт создать две активные
поездки одному водителю. В `ErrDriverBusy` переводится только нарушение
этого индекса.

Для завершения usecase вызывает `Trip.Finish`. Репозиторий выполняет
`UPDATE ... WHERE status = 'active' RETURNING ...`. Это защищает от
повторного завершения и второй записи истории при параллельных запросах.

## Проверки

| Команда | Что делает |
|---|---|
| `make generate` | Генерирует OpenAPI и gomock. Версии инструментов закреплены в `go.mod` |
| `make lint` | Запускает обязательные линтеры курса, gofumpt и gci |
| `make test` | Запускает все unit-тесты с `-race`, затем считает покрытие domain/usecase |
| `make test-integration` | Проверяет работу с PostgreSQL с `-race`, тегом `integration` и `-count=2` |
| `make test-mutation` | Запускает Gremlins и дополнительные мутации. Нужен Python 3 |

`make test` выводит покрытие каждого доменного пакета и usecase, затем общий
результат через `go tool cover`. Моки создаются через `go:generate` рядом
с кодом в `mocks_test.go`. Для unit-тестов БД и коллектор не нужны.

Интеграционные тесты берут `DATABASE_URL` из окружения TripGo. Каждый тест
создаёт схему со случайным именем, применяет исходные миграции и удаляет
схему через `t.Cleanup`. Таблицы приложения при этом не очищаются.

Тесты проверяют сохранение и чтение поездки, историю, доменные ошибки,
параллельные создание и завершение, вложенные транзакции. Полный откат
двух таблиц проверяется при ошибке второго INSERT, ошибке после двух
успешных INSERT, панике и отмене контекста.

`make migrate-down` откатывает последнюю миграцию и удаляет её таблицу.

## Логи, трейсы и метрики

Middleware вызываются в таком порядке

```text
Recover -> Tracing -> Logging -> Metrics -> chi router
```

`otelhttp` создаёт серверный спан и читает W3C `traceparent`. Перед вызовом
хендлера `chi.Match` определяет шаблон маршрута. Поэтому в имени спана,
логах и метриках нет UUID поездки. Для неизвестного пути используется
`unmatched`.

Recover запускает хендлер с буфером ответа. Если происходит паника, тело
и заголовки сбрасываются и заменяются на `500 internal_error`. Готовый ответ
проходит через Metrics, Logging и Tracing до завершения спана. Даже если
хендлер уже вызвал `WriteHeader` или `Write`, клиент получит 500, и тот же
статус попадёт в лог, метрику и трейс. Стектрейс записывается в единственный
лог `request handled`. Счётчик активных запросов уменьшается и при панике.

На каждый запрос пишется одна JSON-запись `request handled` с методом,
шаблоном маршрута, статусом и длительностью. Для 2xx и 4xx используется
уровень Info, для 5xx используется Error. Внутренняя ошибка добавляется
в эту запись один раз. Бизнес-события логируются в usecase после commit.
Обёртка `slog.Handler` берёт `trace_id` и `span_id` из контекста. Вне спана
эти поля пустые. Тела запросов и ответов в логи не пишутся.

`otelpgx` подключён к пулу и создаёт спан на каждый SQL-запрос.
Код в `infra/postgres` добавляет операцию, имя таблицы, SQLSTATE для ошибки
и гистограмму длительности. Набор операций и таблиц ограничен.
SQL и параметры не экспортируются. Для `BEGIN`, `COMMIT` и `ROLLBACK`
коллекция пустая, так как они не относятся к одной таблице.
Репозитории не импортируют OpenTelemetry.

| Метрика OTel | Тип | Атрибуты |
|---|---|---|
| `http.server.request.duration` | histogram, секунды | метод, шаблон маршрута, HTTP-статус |
| `http.server.active_requests` | up-down counter | метод, шаблон маршрута |
| `db.client.operation.duration` | histogram, секунды | операция, коллекция, тип ошибки |
| `tripgo.trips.created` | counter | без дополнительных атрибутов |
| `tripgo.trips.completed` | counter | без дополнительных атрибутов |
| `tripgo.trips.active` | observable gauge | без дополнительных атрибутов |

Границы HTTP- и SQL-гистограмм подобраны для коротких операций.
Встроенные HTTP/SQL-метрики инструментаторов отключены локальным noop meter,
чтобы одни измерения не дублировались с разными лейблами. SDK-провайдеры
передаются явно. Gauge читает число активных поездок из БД, поэтому после
перезапуска процесса значение сохраняется. Бизнес-счётчики растут после commit.

Трейсы и метрики отправляются по OTLP HTTP/protobuf или gRPC. Недоступный
коллектор не мешает запуску и обработке запросов. При остановке сначала
завершаются HTTP-запросы, затем сбор и экспорт телеметрии, после закрывается
БД. На всё действует один `SHUTDOWN_TIMEOUT`.

В Grafana можно импортировать [дашборд](deploy/grafana/trip-service.json)
через Dashboards, New, Import. Он использует источник `prometheus`
из окружения курса. На нём видны запросы и статусы, p95, бизнес-счётчики,
время SQL-запросов и число активных запросов и поездок.
Prometheus заменяет точки в именах метрик подчёркиваниями, добавляет единицы
и суффиксы. Например, получаются `http_server_request_duration_seconds_bucket`
и `tripgo_trips_created_total`.

Результаты и скриншоты находятся в [отчёте о проверке](docs/lab2-verification.md).
Отдельно сохранена [сверка с условием](docs/lab2-audit.md) с журналами запусков.

## Задание со звёздочкой

Для домена и usecase проверил 37 мутаций. Исходные тесты пропускали 8,
после доработки тестов обнаруживаются все 37. Код приложения между этими
прогонами не менялся. Добавлены проверки текста ошибки валидации,
UTC, точности времени и бизнес-логов.

В [отчёте по мутациям](docs/mutation/README.md) разобраны все выжившие
мутации, сохранены результаты до и после, приведены команды для повторного
запуска. `make test-mutation` сохраняет новый результат отдельно от отчётных
прогонов.

## Настройки

Переменные и примеры значений для локального запуска находятся в `.env.example`.

| Переменные | Назначение |
|---|---|
| `HTTP_ADDR` | адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT`, `HTTP_READ_HEADER_TIMEOUT` | таймауты чтения |
| `HTTP_WRITE_TIMEOUT`, `HTTP_IDLE_TIMEOUT` | таймаут записи и простоя |
| `LOG_LEVEL` | debug/info/warn/error |
| `SHUTDOWN_TIMEOUT` | общее время на остановку |
| `DATABASE_URL` | адрес PostgreSQL из `.env` |
| `DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS` | размер пула |
| `DATABASE_MAX_CONN_LIFETIME` | срок жизни соединения |
| `DATABASE_CONNECT_TIMEOUT`, `DATABASE_QUERY_TIMEOUT` | таймаут подключения и операций БД |
| `OTEL_SERVICE_NAME`, `SERVICE_VERSION` | имя сервиса и версия сборки |
| `OTEL_RESOURCE_ATTRIBUTES` | namespace и environment ресурса |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | адрес коллектора из `.env` |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` или `grpc` |
| `OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG` | sampler SDK и его аргумент, если нужен |
| `OTEL_EXPORTER_OTLP_TIMEOUT` | таймаут экспорта в миллисекундах |
| `OTEL_METRIC_EXPORT_INTERVAL` | интервал экспорта метрик в миллисекундах, в примере 5000 |

При запуске проверяются обязательные настройки, положительные таймауты HTTP
и БД, а также `SHUTDOWN_TIMEOUT`. Параметры экспортёров и sampler читает
SDK OpenTelemetry. Для своего окружения нужно подставить адреса
из `tripgoctl connect` вместо примеров в `.env.example`.
